Тестирование безопасности Web и API

Проверка веб-приложений, клиентских кабинетов, backend API и интеграций на практические риски.

Приложение и API — то, чем бизнес на самом деле рискует

Если ваш продукт — это клиентский кабинет, платежный поток, панель управления или мобильное приложение с backend, то именно веб-слой и API держат на себе деньги, данные и репутацию компании. Сетевой периметр можно спрятать за фильтрами и VPN, но приложение обязано быть доступным: клиент должен войти, партнер — вызвать метод интеграции, мобильное приложение — синхронизировать данные. Каждая из этих легитимных дверей одновременно является интерфейсом для злоупотребления, и сканер уязвимостей здесь почти бессилен: логические ошибки авторизации, манипуляции с бизнес-процессом и злоупотребление контрактом API не имеют сигнатур.

Особенность API-рисков в том, что они редко выглядят как «взлом». Атакующий не обходит защиту — он пользуется приложением так, как разработчики не ожидали: подставляет чужой идентификатор в легитимный запрос, вызывает служебный метод, о котором забыла документация, перебирает объекты через интерфейс, который честно отвечает на каждый запрос. Для бизнеса результат тот же, что и при классическом взломе: массовая выгрузка клиентских данных, изменение чужих транзакций, обход платежной логики. Именно поэтому мы рассматриваем веб-приложения и API как отдельный предмет глубокой проверки, а не как пункт в чек-листе внешнего пентеста (о периметре в целом — страница внешнего пентеста).

Что входит в проверку

Основой служат три взаимодополняющих документа OWASP: Web Security Testing Guide задает состав и последовательность проверок, Application Security Verification Standard — планку требований, относительно которой оцениваются механизмы защиты, а OWASP API Security Top 10 — классы рисков, специфичные для программных интерфейсов.

  • Аутентификация и управление сессиями. Логика входа, восстановления доступа и смены пароля, устойчивость сессионных механизмов, поведение при параллельных сессиях, работа второго фактора и точки, где его можно обойти архитектурно.
  • Контроль доступа и авторизация на уровне объектов. Самый частый и самый недооцененный класс: может ли пользователь A читать или изменять данные пользователя B; отделены ли клиентские роли от административных; проверяются ли права на каждом уровне, а не только в интерфейсе.
  • Бизнес-логика. Манипуляции с суммами, статусами, лимитами и последовательностью шагов процесса; сценарии, в которых приложение формально работает «по правилам», но правила составлены с разрывом.
  • Классы инъекций и обработка ввода. Проверка серверной и клиентской обработки данных по каркасу WSTG — без публикации в отчете готовых к переиспользованию атакующих конструкций.
  • Специфика API и интеграций. Избыточная экспозиция данных в ответах, недокументированные и устаревшие версии методов, отсутствие ограничений на частоту и объем запросов, доверие между сервисами и партнерскими интеграциями.

Неаутентифицированный и аутентифицированный режимы

Тестирование без учетных записей отвечает на вопрос «что видит и может посторонний». Аутентифицированное тестирование — «что может ваш клиент, партнер или сотрудник сверх выданных ему прав». Второй режим почти всегда продуктивнее по глубине: подавляющая часть значимых дефектов авторизации и бизнес-логики видна только изнутри учетной записи.

РежимМодель нарушителяЧто показывает
Без учетных записейВнешний наблюдательЭкспозиция, аутентификация «в лоб», утечки в ответах
С учетными записямиКлиент, партнер, младшая рольГоризонтальная и вертикальная эскалация, логика процесса
Несколько ролейВзаимодействие ролейРазрывы между ролевыми моделями и реальными проверками

На этапе scoping мы согласовываем модель тестовых учетных записей: какие роли выдаются, на какой среде, с какими данными. Это режимы исполнения одной услуги, а не отдельные продукты — подробнее о режимах на странице методологии.

Дисциплина исполнения

Активная фаза начинается только после письменного разрешения владельца приложения: без него подобные действия подпадают под статьи 359 и 363 УК РА. Перед стартом фиксируются границы (домены, среды, версии, интеграции, исключения), временные окна, правила взаимодействия и канал экстренной связи. Если проверяется продакшен, отдельно согласовываются ограничения: обращение с реальными клиентскими данными, запрет нагрузочных и деструктивных проверок, порядок действий при обнаружении следов чужой компрометации. Общий каркас процесса соответствует NIST SP 800-115.

Каждая значимая находка проходит ручную валидацию: мы воспроизводим сценарий в минимально необходимом объеме и фиксируем доказательства так, чтобы разработчик мог повторить проверку сам. В отчет не попадают неподтвержденные гипотезы автоматических инструментов.

Типичные классы находок и их цена для бизнеса

  • Разрывы объектной авторизации (IDOR/BOLA). Доступ к чужим записям через подмену идентификатора — прямой путь к массовой утечке клиентской базы и обязательствам перед субъектами данных и регулятором.
  • Слабые места аутентификации и сессий. Захват учетной записи означает действия от имени клиента: вывод средств, смену реквизитов, доступ к документам.
  • Ошибки бизнес-логики. Обход лимитов, манипуляция суммами и статусами — потери, которые не видны в логах как «атака» и потому длятся месяцами.
  • Избыточные данные в ответах API. Интерфейс отдает больше, чем показывает экран: скрытые поля становятся утечкой без единой «взломанной» системы.
  • Забытые версии и теневые методы. Старый эндпоинт без современных проверок обнуляет защиту нового: атакующий всегда выбирает самую слабую дверь.
  • Слепое доверие между сервисами. Компрометация одной интеграции превращается в компрометацию всех, кто ей верит без собственной проверки.

По каждому классу отчет связывает техническую суть с конкретным бизнес-риском: чьи данные, какие функции, какой сценарий давления со стороны клиентов, партнеров или регулятора.

Remediation и retest

Итог работы — не перечень дефектов, а план действий с приоритетами: исправления кода, изменения конфигурации, корректировки API-контрактов и — что важнее — рекомендации процессного уровня, чтобы класс проблемы не воспроизводился в следующем релизе. После исправлений критичные находки проходят повторную проверку (retest) с фиксацией результата в итоговых материалах. Состав отчетных документов описан на странице deliverables.

Регуляторный и отраслевой контекст

Для платежных организаций и операторов электронных денег ЦБ РА подчеркивает ожидания в области кибербезопасности и операционной устойчивости; клиентские кабинеты и платежные API — первое, на что смотрят и партнеры, и проверяющие. Поставщики услуг криптоактивов работают в рамках лицензирования и надзора ЦБ, где безопасность платформы — условие доверия. Для компаний, обрабатывающих большие объемы персональных данных, дефект авторизации в API — это готовый сценарий инцидента по закону о персональных данных. Результаты тестирования помогают подготовиться к таким проверкам и вопросам, но не являются юридическим заключением о соответствии.
