Режимы

Без учётных записей, с учётными записями, несколько ролей — режимы исполнения одной услуги.

01 — Приложение обязано быть доступным

Каждая легитимная дверь — интерфейс для злоупотребления

Сетевой периметр можно спрятать за фильтрами и VPN, но приложение обязано быть доступным: клиент должен войти, партнёр — вызвать метод интеграции, мобильное приложение — синхронизировать данные. Сканер здесь почти бессилен: логические ошибки авторизации и злоупотребление контрактом API не имеют сигнатур.

Атакующий не обходит защиту — он пользуется приложением так, как разработчики не ожидали: подставляет чужой идентификатор, вызывает забытый метод, перебирает объекты через интерфейс, который честно отвечает на каждый запрос.

Тот же результат, что и «взлом»

Массовая выгрузка клиентских данных, изменение чужих транзакций, обход платёжной логики — без единой «взломанной» системы, только через легитимные запросы.

02 — Что входит в проверку

Пять взаимодополняющих областей

Основой служат три документа OWASP: WSTG задаёт состав проверок, ASVS — планку требований, API Security Top 10 — классы рисков интерфейсов. Раскройте область, чтобы увидеть детали.

Логика входа, восстановления доступа и смены пароля, устойчивость сессионных механизмов, поведение при параллельных сессиях, работа второго фактора и точки, где его можно обойти архитектурно.

OWASP ASVS

Самый частый и недооценённый класс: может ли пользователь A читать или изменять данные пользователя B; отделены ли клиентские роли от административных; проверяются ли права на каждом уровне, а не только в интерфейсе.

OWASP WSTG

Манипуляции с суммами, статусами, лимитами и последовательностью шагов процесса; сценарии, в которых приложение формально работает «по правилам», но правила составлены с разрывом.

Проверка серверной и клиентской обработки данных по каркасу WSTG — без публикации в отчёте готовых к переиспользованию атакующих конструкций.

OWASP WSTG

Избыточная выдача данных в ответах, недокументированные и устаревшие версии методов, отсутствие ограничений на частоту и объём запросов, доверие между сервисами и партнёрскими интеграциями.

03 — Как проходит работа

Дисциплина исполнения по этапам

01 · Определение объёма работ

Фиксируются границы: домены, среды, версии, интеграции и исключения; временные окна, правила взаимодействия и канал экстренной связи. Активная фаза — только после письменного разрешения (ст. 359 и 363 УК РА).

02 · Модель тестовых учётных записей

Согласуется, какие роли выдаются, на какой среде и с какими данными. Аутентифицированное тестирование почти всегда продуктивнее по глубине.

03 · Ручное тестирование

Если проверяется боевая среда — отдельно согласуются обращение с реальными данными, запрет нагрузочных и деструктивных проверок, порядок действий при обнаружении следов чужой компрометации.

04 · Валидация находок

Каждая значимая находка воспроизводится в минимально необходимом объёме; доказательства фиксируются так, чтобы разработчик мог повторить проверку сам. Неподтверждённые гипотезы инструментов в отчёт не попадают.

05 · Устранение и повторная проверка

План с приоритетами: исправления кода, конфигурации, контрактов API и рекомендации процессного уровня, чтобы класс проблемы не воспроизводился в следующем релизе. Критичные находки проходят повторную проверку.

Режим тестирования

Тестирование без учётных записей отвечает на вопрос «что видит и может посторонний»: экспозиция, аутентификация «в лоб», утечки в ответах.

Аутентифицированное тестирование — «что может ваш клиент, партнёр или сотрудник сверх выданных прав»: горизонтальная и вертикальная эскалация, логика процесса.

Взаимодействие ролей вскрывает разрывы между ролевыми моделями и реальными проверками прав на каждом уровне.

Это режимы исполнения одной услуги, а не отдельные продукты. Модель тестовых учётных записей согласуется на этапе согласования объёма.

04 — Типичные классы находок

Что находим и что это значит для бизнеса

По каждому классу отчёт связывает техническую суть с конкретным бизнес-риском: чьи данные, какие функции, какой сценарий давления со стороны клиентов, партнёров или регулятора.

ID Класс находки · бизнес-риск Уровень
F1 Разрывы объектной авторизации (IDOR/BOLA). Доступ к чужим записям через подмену идентификатора — прямой путь к массовой утечке клиентской базы. ВЫС
F2 Слабые места аутентификации и сессий. Захват учётной записи — действия от имени клиента: вывод средств, смена реквизитов, доступ к документам. ВЫС
F3 Ошибки бизнес-логики. Обход лимитов, манипуляция суммами и статусами — потери, которые не видны в журналах как «атака» и потому длятся месяцами. ВЫС
F4 Избыточные данные в ответах API. Интерфейс отдаёт больше, чем показывает экран: скрытые поля становятся утечкой без единой «взломанной» системы. СРЕД
F5 Забытые версии и теневые методы. Старый метод без современных проверок обнуляет защиту нового: атакующий выбирает самую слабую дверь. СРЕД
F6 Слепое доверие между сервисами. Компрометация одной интеграции превращается в компрометацию всех, кто ей верит без собственной проверки. СРЕД

Технические находки с планом действий

06 — Устранение и повторная проверка

Чтобы класс проблемы не вернулся в следующем релизе

Немедленно

Исправления кода и конфигурации, закрывающие прямой доступ к чужим данным и функциям.

Ближайший цикл

Корректировки контрактов API, версий и ролевых моделей в плановом релизе.

Системная работа

Процессы разработки, при которых класс дефекта не воспроизводится. Повторная проверка подтверждает результат.

07 — Регуляторный контекст и источники

Для платёжных организаций и операторов электронных денег ЦБ РА подчёркивает ожидания в области кибербезопасности и операционной устойчивости; клиентские кабинеты и платёжные API — первое, на что смотрят и партнёры, и проверяющие. Для поставщиков услуг криптоактивов безопасность платформы — условие доверия.
